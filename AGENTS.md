- When executing a plan, copy the plan to the plans/ directory, and the copied file will be named YYYY-MM-DD-{up-to-three-kebab-words}.plan.md. When the work ends, set the copy's todos to `completed` and add a short Outcome section.
- The HTML exists to make the structure of vibe-coded code legible, so a reader can audit it without wading through a million lines of implementation. A page answers structural questions: what each crate is for, which crates are facades and which implement them, what a user of each facade can name, and where each piece is written. Every rendering choice serves that goal: show declarations and their comments, never bodies; put the public API first; make every item traceable to its file and line; and leave out anything that makes a page longer without making its structure clearer.
- When a rendering case is not covered by a written rule, make each signature and shape in the markdown's records read like one line of Rust source with the bodies removed, and the HTML look like a C++ header that uses Rust's item keywords and visibility labels: a type's data members first, then the members of all its impls merged into the same block. A facade's page shows only what its users can name. A written rule always beats either look. Pin every such choice with a golden test.
- The markdown is JSON Lines whose typed schema lives in `src/md/slop/schema.rs` and `src/md/slop/catalog.rs`; a new kind or field changes those types, the schema check in `src/md/slop/check.rs`, and the goldens together. Its goldens hold no link and show every source line as 0. The markdown is contextual to the run: a change in one crate may change another crate's markdown, but an HTML page changes only with its own crate and the crates it links to.
- The golden files (`expected.md`, `expected.html`) are the specification. Change one only for an intended output change, in the same commit, after reading its diff. Never regenerate goldens to make a failing test pass.
- Never push a tag. Tagging is reserved for the human, because a version tag starts the release workflow, which builds the release and publishes the crate to crates.io. So no `git tag` followed by a push, no `git push --tags`, no `git push origin <tag>`, no force-moving the `nightly` tag, and no `gh release create`, which creates a tag. Pushing branches to `master` stays allowed when the user has said to push.

## Structural rules

- A file holds one concept and has no length limit. Split a file only when it holds a second unrelated concept. Size limits sit on functions and types: clippy holds a function to 100 lines and 7 arguments, and `tests/it/type_size.rs` holds a type to 25 inherent methods across its `impl` blocks and a struct to 12 named fields. Split an oversized type by responsibility; a new entry in that test's `ALLOWED` list is a plan decision with a reason, never a way to make a change pass.
- Production code uses the standard module layout: `foo.rs`, with `foo/bar.rs` for its children, and never `mod.rs`. No `#[path]`, apart from the test files below and the build script's `build/structure.rs`, which `tests/it/structure.rs` shares, and no inline `mod` blocks but tests. A module never has exactly one child file (tests aside): merge it, or make it a peer module `foo_bar.rs` declared beside `foo.rs`.
- The HTML code is below `src/html` and the markdown code is below `src/md`. Neither names a module of the other: `build/structure.rs` fails the build on a `crate::md` path below `src/html` and on a `crate::html` path below `src/md`. Code that both use stays outside the two folders, as does the code that runs both.
- Test code goes at the bottom of the file under test in a `#[cfg(test)] mod tests { }` block when practical, and otherwise in `foo-tests.rs` beside it, wired with `#[path = "foo-tests.rs"] mod tests;`. A big test file may split by topic into siblings named after it, `foo-tests-topic.rs`. Top-level `tests/` trees follow Cargo's conventions.
- Pseudo-random test input comes only from a fixed seed that the failure prints. Temporary directory names come from the test's name, the process id, and a counter.
- Code written before these rules keeps its layout until its own pass: the `*_tests.rs` test modules that `src/main.rs` declares, and the tests that take their temporary folders from `tempfile`.
