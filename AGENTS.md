- When executing a plan, copy the plan to the plans/ directory, and the copied file will be named YYYY-MM-DD-{up-to-three-kebab-words}.plan.md. When the work ends, set the copy's todos to `completed` and add a short Outcome section.
- When a rendering case is not covered by a written rule, make each signature and shape in the markdown's records read like one line of Rust source with the bodies removed, and the HTML look like a C++ header. A written rule always beats either look. Pin every such choice with a golden test.
- The markdown is JSON Lines whose typed schema lives in `src/render_slop_schema.rs` and `src/render_slop_catalog.rs`; a new kind or field changes those types, the schema check in `src/render_slop_check.rs`, and the goldens together. Its goldens hold no link and show every source line as 0. The markdown is contextual to the run: a change in one crate may change another crate's markdown, but an HTML page changes only with its own crate and the crates it links to.
- The golden files (`expected.md`, `expected.html`) are the specification. Change one only for an intended output change, in the same commit, after reading its diff. Never regenerate goldens to make a failing test pass.
- Never push a tag. Tagging is reserved for the human, because a version tag starts the release workflow, which builds the release and publishes the crate to crates.io. So no `git tag` followed by a push, no `git push --tags`, no `git push origin <tag>`, no force-moving the `nightly` tag, and no `gh release create`, which creates a tag. Pushing branches to `master` stays allowed when the user has said to push.
